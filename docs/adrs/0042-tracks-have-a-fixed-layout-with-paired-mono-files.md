# ADR-0042 — Tracks have a fixed layout with paired mono files for stereo, clips stack in layers, and edits return their inverse

- **Status:** Accepted
- **Decided by:** Chris Paro
- **Date:** 2026-11-06
- **Issue:** #38
- **Architecture:** [Editing model](../architecture/project.md#editing-model)


## Context

Building `project_model` (#38) on [ADR-0037](0037-overlapping-clips-the-later-covers-with-a-short.md)
left three questions, put to the developer. How does a track's channel layout relate to stored
audio, given that every channel is its own mono file
([ADR-0014](0014-project-audio-is-stored-as-mono-32-bit-float-wav.md))? Does the undoable model
include mixer and routing state? And how are the property tests the issue asks for written, when
a core crate may depend on nothing beyond `thiserror`? Building the crate also needed a way to
represent "the clip on top" and the reversibility of edits.

## Decision

- **Track layout:** a track is mono or stereo, fixed when it is created. A mono track's clips
  reference one stored file. A stereo track's clips reference a left and a right mono file, read
  at one shared offset and length.
- **Layers:** each track keeps its clips in layer order. A clip that is added, moved, or given a
  new position goes to the top layer. Trims, gain and fade changes keep its layer. A clip keeps
  its id when it moves between tracks.
- **Edits:** applying an edit returns the edit that reverses it exactly; a refused edit changes
  nothing. A gesture made of several changes is one batch edit, undone as one. Restoring a named
  version replaces the whole state and is reversible like any other edit. Saving a version is not
  an edit. Ids are never reused within a session.
- **Routing:** mixer and routing state is not part of `project_model` for now. A follow-up ticket
  models its saved, undoable form.
- **Property tests:** randomized edit sequences are generated by a small seeded generator in the
  test code. No property-testing crate is used, and a failure reports its seed.

## Alternatives considered

- **Changeable track layout** — clips would have to be converted or refused when the layout
  changed, for little benefit over making a new track.
- **Layout per clip** — a track could mix mono and stereo clips, so its graph node's layout would
  vary along the timeline.
- **A layer number on each clip** — duplicates the order already held by the clip list, and the
  two could disagree.
- **Snapshots of the whole state per undo step** — simple and exact, but memory grows with the
  project size times the history depth, which is unlimited
  ([ADR-0012](0012-undo-is-unlimited-per-session-and-named-versions.md)).
- **Routing in this crate now** — widens #38 before the persisted form of the graph is designed.
- **`proptest`** — shrinking and better reports, but a dependency in a core crate, against the
  crate rules.

## Consequences

- The engine plays a stereo track's clips from two read-ahead streams.
- Without shrinking, a failing random sequence must be cut down by hand from its seed.
- Routing edits will join `Edit` as new variants.
